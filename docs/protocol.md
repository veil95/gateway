## Два канала связи

| Канал | Для чего |
|---|---|
| **HTTP** | регистрация, вход, обновление токена, получение билета, история чата |
| **WebSocket** | отправка сообщений и всё, что приходит в реальном времени |

Правило: всё, что должно прийти **само** (новое сообщение, «печатает»), идёт по WebSocket. Всё остальное — обычным HTTP.

## Подключение и авторизация

### Шаги

```
1. POST /auth/login                      → access-токен в теле, refresh в cookie
2. POST /ws-ticket  (Authorization: Bearer <access>)   → одноразовый билет
3. new WebSocket("wss://<gateway>/ws?ticket=<билет>")  → линия открыта
```

### Почему билет, а не токен

Браузерный `WebSocket` не умеет отправлять заголовок `Authorization`. Передавать access-токен в адресе нельзя: адреса попадают в логи серверов и прокси. Поэтому фронт сначала меняет токен на **короткоживущий билет** и подключается уже с ним.

- билет живёт **30 секунд** и предназначен для одного подключения
- получать билет нужно **перед каждым** подключением, в том числе при переподключении

> **Пока не реализовано.** Эндпоинт `/ws-ticket` ещё не написан. На время разработки gateway принимает access-токен прямо в адресе: `ws://<gateway>/ws?access_token=<токен>`. Для локальных проверок это годится, но закладываться на такой способ не стоит — он будет заменён на билет без предупреждения.

### Коды закрытия соединения

| Код | Что значит | Что делать фронту |
|---|---|---|
| `1008` | билет негодный или просрочен | получить новый билет; если и он не принят — обновить access-токен, затем на экран входа |
| `1013` | сервис временно недоступен | подождать и переподключиться, увеличивая паузу (1с, 2с, 4с, …) |
| `1000` | штатное закрытие | переподключаться не нужно |

Важно: **ошибка в команде соединение не рвёт**. Если соединение закрылось — значит, проблема с подтверждением личности или с сервисом, но не с тем, что прислал клиент.

## Формат сообщений WebSocket

Все сообщения в обе стороны — JSON с одинаковой внешней структурой.

### От клиента к серверу — команда

```json
{
  "type": "send_message",
  "request_id": "6f1c0e2a",
  "payload": { "chat_id": 55, "body": "привет" }
}
```

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `type` | строка | да | имя команды из таблицы ниже |
| `request_id` | строка | да | метка клиента, по ней придёт ответ. Любая уникальная строка в пределах соединения |
| `payload` | объект | да | содержимое команды, своё для каждого `type` |

### От сервера к клиенту — три вида

**Ответ на команду** — с тем же `request_id`:
```json
{ "type": "message_sent", "request_id": "6f1c0e2a", "payload": { ... } }
```

**Ошибка команды** — тоже с `request_id`:
```json
{ "type": "error", "request_id": "6f1c0e2a", "error": { "code": "user_not_in_chat", "message": "..." } }
```

**Событие** — без `request_id`, клиент о нём не просил:
```json
{ "type": "message_created", "payload": { ... } }
```

**Правило для фронта:** есть `request_id` — это ответ на твою команду, ищи её у себя; нет — это событие, просто обнови интерфейс.

### Зачем `request_id`

По WebSocket ответы приходят в произвольном порядке. Если пользователь быстро отправил три сообщения, без метки невозможно понять, какое подтверждение к какому относится.

Рекомендуемое поведение фронта:
1. сгенерировать `request_id`, показать сообщение в интерфейсе как «отправляется»
2. запомнить связь `request_id` → сообщение на экране
3. пришёл `message_sent` — пометить отправленным, подставить настоящие `message_id` и время
4. пришёл `error` — показать ошибку и кнопку «повторить»

## Команды

### `send_message` — отправить сообщение

**payload:**

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `chat_id` | int | да | чат, в который отправляется сообщение |
| `body` | строка | да | текст, от 1 до 4000 символов |
| `reply_to_message_id` | int | нет | идентификатор сообщения, на которое это ответ |

**Ответ `message_sent`:**
```json
{
  "type": "message_sent",
  "request_id": "6f1c0e2a",
  "payload": {
    "message_id": 981,
    "chat_id": 55,
    "user_id": "f1390d71-8e96-479b-a457-3eb48d64dc93",
    "body": "привет",
    "reply_to_message_id": null,
    "created_at": "2026-10-04T12:30:01Z"
  }
}
```

Время создания проставляет сервер — фронту следует показывать именно его, а не момент нажатия кнопки.

**Возможные ошибки:** `invalid_payload`, `user_not_in_chat`, `chat_service_unavailable`.

### `typing` — пользователь печатает

**payload:**

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `chat_id` | int | да | чат, в котором идёт набор текста |

**Ответа нет.** Остальные участники чата получат событие `typing`.

Рекомендация: отправлять не чаще одного раза в 3 секунды, пока человек печатает.

**Возможные ошибки:** `invalid_payload`, `user_not_in_chat`.

## События

### `message_created` — в чате появилось новое сообщение

Приходит всем участникам чата, кроме автора: автор уже получил `message_sent`.

```json
{
  "type": "message_created",
  "payload": {
    "message_id": 982,
    "chat_id": 55,
    "user_id": "a3ec66ae-3033-464d-a295-5ca5ee701876",
    "body": "и тебе привет",
    "reply_to_message_id": 981,
    "created_at": "2026-10-04T12:30:14Z"
  }
}
```

### `typing` — участник чата печатает

```json
{
  "type": "typing",
  "payload": {
    "chat_id": 55,
    "user_id": "a3ec66ae-3033-464d-a295-5ca5ee701876"
  }
}
```

Приходит всем участникам, кроме самого печатающего. Индикатор стоит скрывать через 5 секунд, если событие не повторилось.

## Ошибки

Ошибка команды приходит сообщением типа `error` и **не разрывает соединение**.

```json
{
  "type": "error",
  "request_id": "6f1c0e2a",
  "error": {
    "code": "user_not_in_chat",
    "message": "User is not a member of this chat"
  }
}
```

- **`code`** — для программы. Фронт принимает решения по нему
- **`message`** — для разработчика, в логи. Показывать пользователю не нужно: тексты на английском и могут меняться

### Коды

| Код | Когда | Что делать фронту |
|---|---|---|
| `unknown_command` | неизвестный `type` | ошибка в коде клиента, показывать пользователю нечего |
| `invalid_payload` | не хватает поля или неверный тип | то же: это баг клиента |
| `user_not_in_chat` | отправитель не участник чата | сообщить пользователю, обновить список чатов |
| `user_not_found` | пользователь не найден | обновить данные |
| `chat_service_unavailable` | хранилище временно недоступно | показать «не отправлено», дать кнопку «повторить» |

### Сообщение не удалось разобрать

Если присланный текст не является корректным JSON, связать ошибку с командой невозможно: `request_id` взять неоткуда. В этом случае приходит отдельный тип — **`protocol_error`**, без `request_id`:

```json
{
  "type": "protocol_error",
  "error": {
    "code": "invalid_json",
    "message": "Message is not valid JSON"
  }
}
```

Пометить конкретное сообщение в интерфейсе по нему нельзя — остаётся показать общую ошибку и записать в лог. Соединение при этом не разрывается.

Если JSON разобрался, но не прошёл проверку конверта или `payload`, приходит обычный `error` с `request_id` — связь с командой сохраняется.

## HTTP-эндпоинты

Все запросы идут на gateway.

| Метод и путь | Зачем | Тело запроса | Ответ |
|---|---|---|---|
| `POST /auth/register` | регистрация | `username`, `display_name`, `password_plaintext` | 201, `user_id` |
| `POST /auth/login` | вход | `username`, `password` | access-токен в теле, refresh в httponly-cookie |
| `POST /auth/refresh` | обновить access-токен | — (refresh берётся из cookie) | новый access-токен |
| `GET /auth/me` | данные текущего пользователя | — | `user_id`, `username`, `display_name` |
| `POST /ws-ticket` | получить билет для WebSocket | — | билет, срок жизни 30 секунд |
| `GET /chats/{chat_id}/messages` | история чата | — | список сообщений, постранично |

Access-токен передаётся заголовком `Authorization: Bearer <токен>`.

### История сообщений

История листается **курсором**, а не номером страницы: пока человек листает вверх, в чат приходят новые сообщения, и нумерация страниц сдвигалась бы.

| Параметр | Описание |
|---|---|
| `cursor` | `message_id`, начиная с которого отдавать более старые. В первом запросе не указывается |
| `per_page` | сколько сообщений вернуть, по умолчанию 20 |

## Чего пока нет

Эти возможности появятся позже. Команды и события для них уже зарезервированы, но сервер их **не принимает**:

- создание чата, добавление и исключение участников, выход из чата
- изменение и удаление сообщений
- отметка «прочитано»
- стикеры и вложения
- статус «в сети»

Конверт и правило `request_id` при их появлении не изменятся — добавятся только новые значения `type`.
